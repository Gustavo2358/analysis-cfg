# JSON Zstandard — pronto para revisão

Os artefatos dos 14 casos passaram de **953.618 MB para 63.968 MB**: redução de **93.29%**. MB = 1.000.000 bytes; são bytes de arquivos, incluindo os aliases publicados.

Nos cinco programas CardDemo medidos três vezes, a mediana da soma das quatro etapas passou de **85.745 s para 86.051 s**: **+0.307 s (+0.36%)**. Esse é o efeito líquido observado de compressão, descompressão, I/O e inicialização da biblioteca na execução completa. Os totais variaram de 84,998–86,703 s no baseline e 85,253–86,147 s no candidato; os intervalos se sobrepõem.

## Implementação

- Frontend publica os quatro JSONs gerados como `.json.zst` por padrão; `--json-compression none` é a opção explícita de diagnóstico/fixtures.
- Lower, CFG e análise aceitam JSON legado e Zstandard. Destinos explícitos `.json.zst` selecionam compressão; `.json` mantém a saída legível solicitada pelo caller.
- Bundle `dependency-input`, AIR, source evidence, CFG, dependências, dataflow e relatório regional suportam compressão. Os hashes de correlação identificam JSON descomprimido; recibos de entrega identificam os bytes físicos do arquivo.
- `zstd-jni` 1.5.7-20, nível 3, uma thread e checksum. Sem mudanças nos modelos, schemas, versões ou algoritmos semânticos. Configurações, fixtures, fontes e evidências históricas preservadas.
- A biblioteca `air-java` e a especificação `analysis-ir` permanecem nos baselines: elas não produzem arquivos na pipeline; seus codecs em memória continuam representando JSON.

## Método e limites

- JVMs independentes; Java 21.0.12.1, `-Xms256m -Xmx2g -XX:+UseG1GC`; mesmos inputs, copybooks, opções e máquina. Jars congelados antes dos runs. Nenhum build concorrente durante o benchmark.
- Etapas: frontend → lower/bundle → CFG → dependências. Tempo medido envolve a CLI inteira e os arquivos produzidos. Verificação, hashes externos, builds e escrita do relatório ficam fora do intervalo de cada etapa.
- Ordem baseline/candidato invertida na segunda repetição. A comparação diferencial anterior funciona como aquecimento de caches do sistema; cada run continua inicializando uma JVM nova.
- Três repetições por programa são uma medição local, sem inferência de significância estatística ou garantia para todo corpus/hardware. Min/max e cada comando/exit code/tempo/CPU/RSS estão preservados.
- O efeito líquido pode ser negativo porque gravar menos bytes pode compensar o trabalho de compressão. Esta medição não isola exclusivamente o tempo de CPU do algoritmo Zstandard.
- O launcher de dataflow continua emitindo seu recibo JSON em stdout; o produto persistido pode ser comprimido. Metadados de build de Maven e arquivos de configuração continuam sob seus formatos próprios.

Esse repositório de evidências permanece local, sem remote.

Os baselines da tabela foram compilados em worktrees separados. Os runtimes
foram congelados em jars e conferidos por SHA-256 antes/depois das comparações.
Os hashes das fontes de produção demonstram equivalência entre o candidato
medido e os commits de implementação acima. As linhas de comando seguem
[o contrato de transporte](../engineering/json-zstd.md).

Para conferir os agregados publicados:

